# CloudBase 一次配置、后续自动更新

目标：保留当前聊天/加密实现和单活动实例保护，减少部署参数，改用代码仓库持续部署，避免每次上传 ZIP。

选择原则：优先 CloudBase 原生 Git 持续部署；不引入额外云平台、前端 SDK 或新的应用依赖。若该入口不支持自动触发，使用官方支持的 CI 部署命令，不虚构配置字段。

实施与验收：
1. 确认官方容器持续部署入口和 Git 推送触发能力，记录来源。
2. 先补配置回归：生产默认使用 CloudBase，但仍强制校验环境 ID/服务端密钥，禁止文件存储。
3. 固化容器端口、集合名、存储驱动等默认值；构建阶段先类型检查/测试，失败不产出生产镜像。
4. 使用 CloudBase 控制台原生 GitHub/GitLab 授权绑定与自动部署，不新增第三方 CI 密钥；镜像内固定构建版本戳，通过数据库事务请求旧实例停止并交接租约，不能直接抢占有效租约。教程只保留首次操作、日常推送、失败恢复。
5. 运行配置回归、全部单测、类型检查、构建、源码打包完整性检查；未取得凭证不实际操作云资源。

边界：云账户首次授权、付费资源/域名/密钥无法在本地代办；不能声称已经开启云端自动更新。部署可能短暂断线，不能为自动发布取消数据库租约或权限保护。

官方依据：https://docs.cloudbase.net/run/deploy/deploy/deploying-git 支持授权绑定仓库/分支、启用自动部署并配置 Webhook；只填写公开仓库 URL 不等于完成持续部署。https://docs.cloudbase.net/run/faq/server 说明副本数按版本生效，旧版本可能存活，因此需要应用内安全交接。

回退边界：Docker 可复用精确旧源码层，因此提供已跟踪 deployment-version.txt 和 npm run release:refresh，只在回退/原样重发时刷新并一并提交；生产部署串行，等待当前完成再推下一次。

本地验收：15文件101项单测、四工作区类型检查、协议检查、构建通过；Git持续部署未操作云账户。
