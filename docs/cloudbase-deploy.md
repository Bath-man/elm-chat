# CloudBase：无数据库单实例部署与 Git 自动更新

使用腾讯 CloudBase 容器型云托管，保留根目录 Dockerfile 和原生 Git 自动部署。应用不使用服务端数据库，不保存房间元数据文件，也不需要 CloudBase SDK、数据库集合、API Key 或租约交接。

## 首次配置

1. **仓库**：把源码放进自己的 Git 仓库，生产分支使用 `main`；根目录保留 `Dockerfile`、`package.json` 和 `apps/`。不要提交 `node_modules`、`.env`、本机聊天记录或云端密钥。
2. **原生 Git 部署**：在容器云托管中授权绑定仓库和 `main`，开启自动部署及 Webhook。构建目录为仓库根目录，使用现有 `Dockerfile`。
3. **容器**：端口 `8080`，提供无需访客登录的公网 HTTPS/WebSocket，运行镜像默认命令 `node apps/server/dist/index.mjs`。不要使用 PM2 集群、Node cluster、多进程启动或多副本。
4. **实例**：最大实例 `1`；最小实例可选 `0` 或 `1`。`0` 允许闲置缩零，但缩零会丢失全部房间；`1` 可减少闲置回收和冷启动，仍不能避免重启、故障回收或部署导致的房间丢失。
5. **发布策略**：整个生产服务只能有一个活动实例、一个 Node 进程。不要跨版本分配流量，也不要保留可访问的旧版本入口。**最大实例 `1` 不等于跨版本全局单实例**；若平台发布过程会并行启动新旧版本，须采用先停止旧实例、断开旧 WebSocket，再启动/切到唯一新实例的方式，接受维护中断。不要把自动灰度或滚动交叠当作房间无损升级。
6. **变量与探针**：无需应用必填变量或数据库凭证。镜像已设 `NODE_ENV=production`、`PORT=8080`；只有修改端口或静态目录时才需设置 `PORT`、`PUBLIC_DIR`。使用默认 TCP `8080` 健康检查，或支持时使用 `/healthz`、`/readyz`。

这是全新部署，无需旧数据迁移或兼容旧版本。不要创建 `chat_rooms`、`chat_runtime` 集合；自动部署配置中也不需要 `TCB_ENV_ID`、`CLOUDBASE_APIKEY`、`STORAGE_DRIVER`、集合名或 `CHAT_DATA_FILE`。平台账号授权、发布方式和域名/备案在控制台配置；应用不会持有用于管理、停启云实例的高权限凭证。

如果控制台仅提供会并行运行多版本的自动发布方式，需先解决平台侧停旧/启新的串行发布配置，再将其用于生产。保留 Git 自动触发构建不代表应用具备多实例协调能力。

## 日常更新与回退

**main 提交 → CloudBase Webhook → npm ci → 类型检查 → 单测 → 源码 ZIP → 前后端构建 → 镜像发布。**

安装、测试或构建失败不会生成本次运行镜像。发布与回退都必须遵守前述单实例约束；等待当前发布结束再发下一次，不要手动分流，也不要同时对旧版专属地址发送请求。

回退可在 GitHub 网页 Revert 功能 PR 并合并到 `main`，继续走相同 Docker/Git 流程。无需本地重新上传 ZIP 或填写数据库凭证。请保持本版无数据库的部署基础；将旧数据库版本重新上线属于另一套部署方式。

应用不转移房间、不恢复旧房间，也不自动清理云端旧版本或镜像。每次部署和回退后，用户都需新建房间并分享新邀请。停止旧实例可能中断聊天，这是本方案明确接受的行为。

## 房间生命周期与用户体验

- 房间、邀请、准入席位和恢复凭证摘要只存在当前进程内存。服务重启、实例回收、缩容至零、重新部署或回退后，原房间及邀请失效。
- 短暂断网时，只要原进程仍在、房间仍存在，页面会退避重连；快速重试耗尽后每30秒开启新一轮，网络恢复事件可立即重试。
- 元数据请求确认房间不存在（404/410）或已过期/销毁后，页面停止重连并提示重新建房、分享新邀请。原链接不能重新创建旧房间。
- 不清除用户已有浏览器数据。旧房间页面仍可查看、导出本机聊天记录；导入导出完全在浏览器完成，不上传服务器。新房间使用新身份空间，旧房间的待发送内容不会自动转移或发送到新房间。
- 端到端加密保持不变。服务器仅实时转发加密消息，不存储聊天正文、密文历史或用户备份。

## 健康检查与故障处理

- `/healthz`：进程存活。
- `/readyz`：当前进程可以处理请求；关闭期间返回不就绪。就绪不代表任何旧房间仍存在。
- 不再提供用于选主或交接的 `/api/runtime`，客户端不轮询该接口。

遇到冷启动或临时连接错误，先检查服务日志、容器端口、WebSocket 网关和 HTTPS。房间404属于内存状态已经丢失，应新建房间；无需检查数据库权限或删除租约。

如果同一邀请在不同设备上间歇出现404，或者两人无法加入同一房间，优先检查是否运行了多个 Node 进程、多个实例、跨版本流量分配或仍存活的旧 WebSocket。缺少共享状态时，会话粘滞也不能让跨实例的房间恢复为同一个房间。

历史版本和镜像可按需在控制台清理。实例归零不等于版本、镜像或所有费用归零；具体回收时机和计费以平台为准。

## 部署验收与验证边界

首次上线后，用两个独立浏览器创建房间、分享邀请并完成双人加密聊天；短暂断网后验证原房间重连。再提交一次 `main`，确认 Webhook 自动构建发布、旧实例停止且只有新实例接流量，原房间提示失效，新房间可聊天，本机旧记录仍可查看和导出。最后重启实例，确认原邀请失效。

仓库本地验证见 [TEST-RESULTS.md](../TEST-RESULTS.md)。本次没有实际发布到云端，也未验证账号授权、Webhook、平台发布串行性、缩容或真实网关；不要把本地测试通过视为这些云端配置已验收。Docker 构建是否实测以验证结果为准。
