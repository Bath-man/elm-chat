# CloudBase：一次配置，main 自动发布与网页回退

使用容器型云托管 + 文档数据库，不需要 Cloudflare、GitHub Actions 或额外部署工具。

## 首次手动操作清单

1. **仓库**：把源码放进自己的 GitHub 仓库，生产分支 `main`。根目录直接包含 `Dockerfile`、`package.json`、`apps`；不要上传 `node_modules`、`.env` 或 `.data`。
2. **数据库**：创建 CloudBase 环境，以及 `chat_rooms`、`chat_runtime` 两个文档集合，客户端读写规则全部禁止。准备本环境数据库可用的服务端 API Key。
3. **原生 Git 部署**：在容器云托管中授权绑定 GitHub 账号，选择仓库和 `main`，打开“自动部署”（配置 Webhook），发布选“自动灰度”，新版本上线后 **100% 流量到最新版本**，不手动分流。
4. **容器配置**：构建目录为根目录，使用根目录 `Dockerfile`；端口 `8080`，默认 TCP 健康检查；开启无需访客登录的公网 HTTPS/WebSocket。**最小实例 `0`，最大实例 `1`**，允许无流量时缩容至零。
5. **自动部署运行配置**：保存以下两个变量，确认它们用于后续 Git 触发的新版本，不是只临时给某个旧容器添加：

   ```text
   TCB_ENV_ID=你的环境ID
   CLOUDBASE_APIKEY=你的服务端APIKey
   ```

   不需要填存储驱动、集合名或其他变量。密钥不写进 Git、前端、构建参数或 `VITE_*`。平台变量按版本绑定，应用无法代平台复制密钥；务必在自动部署入口保存配置。
6. **清理旧设置**：如果已经有最小实例为 `1` 的历史版本，首次停止不用的版本，或将它们最小实例设为 `0`。新配置不一定追溯修改旧版本。不要保留指向旧版本的流量分配。首次升级后两部手机各刷新一次，让页面加载新的路由检查逻辑。
7. **首次验收**：首次发布后，用两浏览器聊天、发提醒和调查；再从 GitHub 网页修改 README 并提交到 `main`，确认自动触发发布，新版本有上述变量、`/readyz` 在访问聊天室后变为 200，原邀请仍有效。这一步验证你自己的 Webhook 和配置继承，不是额外本地命令。

如果没有 Git 授权/自动部署开关，仅填写公开仓库 URL 不等于完成持续部署。云账号授权、可能的费用确认和域名/备案由你在控制台完成。

## 日常更新：只 push main

在 GitHub 网页编辑并提交，或正常本地 push：

**main 提交 → CloudBase Webhook → npm ci → 类型检查 → 单测 → 源码 ZIP → 前后端构建 → 镜像发布 → 全量切流量 → 请求触发安全接管。**

失败的安装/测试/构建不会生成本次运行镜像。缺少环境变量或启动时无法访问数据库时，进程不开放健康端口，避免把错误配置版本当作健康发布。

部署前无需本地 build、打 ZIP 或填写密钥。同一服务使用一个生产分支，等待当前发布完成再发下一次；不要在多个版本之间手动分流。

## 网页端回退，不需要本地命令

在 GitHub 打开已合并的功能 PR → **Revert** → 创建并合并回退 PR 到 `main`。也可以直接在网页把相关文件恢复成旧内容并提交到 `main`。

这会自动走同一套测试和部署。即使 Docker 复用了完全相同的旧源码镜像，**接管也不再依赖构建时间、镜像新旧或额外版本文件**。无需 `release:refresh`、修改标记、关缓存或本地终端。

请保留本轮的部署基础代码，不要回退到根本不包含这套交接机制的上古版本；跨越这种部署基础变更应先停止不兼容旧版本一次。直接切换旧版本流量并非推荐的代码回退流程。

## 旧实例如何省钱

- 交接后，旧进程断开 WebSocket、排空任务、清空房间缓存并释放租约，停止续租/后台抢租；不会用不停退出重启的方式“清理”。
- 配合 **最小实例 0 + 旧版流量 0**，旧容器无流量后由 CloudBase 缩容至零。无需每次发布后手动停旧版本；也无需给聊天应用管理或删除云服务的高权限。
- 缩容不是即时的，具体等待以平台为准；两个用户都离线后当前版本也可缩容，下次访问冷启动，可能短暂等待。
- 历史版本/镜像仍可能保留，**实例归零不等于自动删除版本或所有费用归零**。镜像、数据库等存储计费按平台规则；有大量历史镜像时可偶尔在控制台清理。
- 不要持续探测旧版专属 URL，不要保留监控请求或流量分流，这些访问会妨碍缩容。仅使用服务的统一生产 HTTPS 地址。

## 交接与短暂 503

数据库事务确保只有一个有效 owner，新版只能登记有时限的接管预约，不能抢占仍有效的旧租约。旧版排空后释放；旧版宕机则等租约过期。写入仍检查 owner/有效期，失去租约的旧连接不能发送聊天帧。

只有新路由来的 API/新 WebSocket 连接可以请求接管；健康探针、静态资源、旧 WS 消息和后台定时器不能反抢。可见聊天室每 15 秒做一次轻量同源 HTTP 检查，使长期连接的旧页面也迁到当前版本；隐藏页面停止这个检查。

切换可能有短暂 503/断线，客户端会重连，不承诺零中断。空闲容器不会无限轮询数据库；后续真正访问可以重新尝试，且恢复时重新加载持久化元数据，不复用旧席位缓存。

- `/healthz`：进程存活，不请求接管。
- `/readyz`：是否持有聊天租约，不请求接管。
- `/api/runtime`：用户页面的路由检查，可唤醒/请求交接，未接管时 503。

**不要把 `/readyz` 设为发布前置健康检查**，否则新版本可能等待切流量，而切流量又等待接管。保留默认 TCP `8080`；若平台支持自定义 HTTP 存活检查，可用 `/healthz`。

持续 503 时检查：最新版本运行变量、数据库权限/集合、是否真的全量切流量、是否仍有客户端访问旧版专属地址。不要删除租约或关闭保护来强行双开。
