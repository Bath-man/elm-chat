# CloudBase：首次配置，之后推送自动更新

使用 **CloudBase 容器型云托管 + 文档数据库**。不要选静态网站托管或普通云函数，也不需要 Cloudflare、Firebase、GitHub Actions 或本地部署 CLI。

## 首次配置（只做一次）

### 1. 把源码放进你自己的仓库

解压源码 ZIP，把项目内的文件放到自己的 GitHub/GitLab 仓库根目录，推荐分支名 `main`。根目录应能直接看到 `Dockerfile`、`package.json`、`apps`。

不要提交 `node_modules`、`.env`、`.data` 或真实密钥。无需手工生成构建文件或上传 `dist`；云端会自动构建，并生成与该版本对应的 `/source.zip`。

### 2. 准备 CloudBase 环境

- 创建环境，记录环境 ID。
- 创建两个文档数据库集合：`chat_rooms`、`chat_runtime`。
- 两集合的**客户端读写均禁止**；浏览器不直接访问数据库。
- 创建有本环境数据库权限的**服务端 API Key**，不要使用客户端公开 Key。

数据库只保存房间元数据、准入身份和运行租约，不保存聊天正文或密文消息队列。

### 3. 绑定仓库并创建容器服务

在云托管选择“通过 Git 仓库部署”，**授权绑定你的 GitHub/GitLab 账号**，然后选择仓库、`main` 分支。

| 配置项 | 填写值 |
| --- | --- |
| 构建目录 | 项目根目录（通常为 `/` 或默认根目录） |
| 构建方式 / 文件 | Dockerfile / `Dockerfile` |
| 容器端口 | `8080` |
| 最小 / 最大副本数 | `1` / `1`，不缩容至零，不自动扩容 |
| 访问方式 | 开启公网 HTTPS / WebSocket，访客无需 CloudBase 登录 |
| 自动部署 | **开启**（平台配置 Webhook） |
| 发布方式 | **自动灰度**，新版本成功后自动切换全部流量；不要手工分流 |

**注意：只粘贴公开仓库 URL 不等于绑定账号、开启自动部署。** 如果没有授权账号或自动部署开关，请先完成官方 Git 仓库绑定流程。

健康检查保留平台默认 TCP `8080`；若支持自定义 HTTP 存活检查，可用 `/healthz`。**不要将 `/readyz` 作为发布前置健康检查**：新版本需要先运行，再通过数据库请求旧版本交接租约，否则会互相等待。

### 4. 只填两个运行环境变量

```text
TCB_ENV_ID=你的环境ID
CLOUDBASE_APIKEY=你的服务端APIKey
```

密钥只在云端运行配置中填写，不放 Git、Dockerfile、构建参数或 `VITE_*`。镜像已经设置 `NODE_ENV=production`，程序默认使用 CloudBase、端口 `8080`、集合 `chat_rooms` / `chat_runtime`，无需再配置存储驱动或集合名。

把变量保存在**用于后续自动部署的服务配置**中，确保每个新版本继承。官方环境变量属于版本配置；若首次页面只给当前版本添加变量，还需在自动部署所用配置中保存，不能只给一个已运行容器临时添加。

点击首次部署。成功后打开 HTTPS 地址，用两个独立浏览器创建房间、邀请、发送提醒/调查。首次云账号授权、密钥和可能的收费确认需要你自己完成。

## 之后更新：只提交代码

在仓库网页编辑并提交，或在本地执行：

```bash
git add .
git commit -m "更新聊天网站"
git push origin main
```

流程自动完成：**推送 → CloudBase Webhook → 安装依赖 → 类型检查和单测 → 生成源码 ZIP → 前后端构建 → 发布镜像 → 全量切换 → 安全交接房间服务**。类型检查/测试/构建失败不会产出本次发布镜像，在云托管构建日志查看原因。

不用反复上传 ZIP、不用每次填写密钥、不用本地运行部署命令。同一服务只绑定一个生产分支；**等待当前发布完成后，再推送下一次生产更新**，不要并行手工发布或让多个构建竞争上线。

## 更新时会发生什么

- 新构建带固定版本戳，重启不会变成“更新版本”。新版本通过数据库事务请求旧版本停止服务，旧版释放后新版接管；不会直接抢占有效租约，也不会取消双人席位保护。
- 交接可能短暂断线或返回 503，网页会重连；不是零中断发布。不要为消除短暂等待而删除租约、禁用保护或开放多副本。
- 原房间元数据保留；聊天记录仍在原域名的浏览器 IndexedDB。不要更换域名或清理网站数据来升级。
- 旧版本自动重启不会反抢新版本。平台保留的旧版本可能仍占资源，按控制台计费/保留策略清理；这不应是每次发布的必要交接步骤。

## 失败处理 / 回退

- **推送不触发**：检查是否推到绑定分支、账号授权/Webhook 和“自动部署”开关。
- **构建失败**：查看构建日志，修复后再次 push；不要跳过测试。
- **持续 503**：检查两个运行变量是否被新版本继承、集合和服务端权限；查看容器日志。`/healthz` 只表示进程存活，`/readyz` 200 才表示持有租约。
- **回退代码或原样重新发布**：先 revert，再刷新一次构建标记，然后一起提交：

  ```bash
  git revert --no-commit 要回退的提交ID
  npm run release:refresh
  git add .
  git commit -m "回退并重新发布"
  git push origin main
  ```

  `release:refresh` 只更新 `deployment-version.txt`，不连接云端。Docker 可能缓存完全相同的旧源码构建；这个新标记保证回退也重新构建。不要省略标记，也不要直接把旧镜像切回生产：旧构建戳不会主动驱逐较新的活动版本。普通修改后的 push 不需要运行它。
- **首次从不支持交接的旧版本升级**：如果你已经部署过之前的手动版本，需要在这次升级时停止旧版本一次；后续本版之间可自动交接。

本地 `npm run dev` 仍无需云端凭证。高级可选变量及代码默认值见 `apps/server/src/config.ts`，日常部署无需填写。

**未使用你的腾讯云账号实际开启自动部署，也未执行真实云数据库/网关或 Docker 镜像构建验收。** 本地验证结果见 [测试结果](../TEST-RESULTS.md)；云资源可能收费，域名/备案按平台要求处理。
